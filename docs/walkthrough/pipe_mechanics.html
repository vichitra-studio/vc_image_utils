vc::pipe — implementation & mechanics

vc_image_utils · implementation & mechanics

Inside vc::pipe

The machinery behind the schematic: how a typed slot<T> lowers to an erased name, how declare() fills a contract, how validate() compares types before any pixel moves, and how run() injects / executes / harvests over a map keyed by stage_port — traced on real data structures, then wired up in real, current-API code.

The one boundary everything turns on

Because a pipeline is composed at runtime (a CLI or config file names stages and slots as strings), types can only live at the authoring edge. The instant a slot crosses into the framework it is lowered: the name is kept as a std::string, the type erased to a std::type_index value.

slot<vc_image>{"rgb"}   // compile-time: type in the type system, name a string_view
      │  add_input_slot / stage_port ctor / ctx.get_input — the boundary
      ▼
slot_decl{ name:"rgb", type:type_index(vc_image) }   // runtime: a value you can store & compare
Three representations, one per job. slot<T> authors (typo-safe, type deduced); the private slot_decl stores (erased, owning); stage_port{stage, slot} is the single wiring currency that connect() and run() both speak. Lowering is one-way — you can recover a name's type as a type_index, never reconstruct a compile-time slot<T>.

Mechanism 1 · the type-erased packet implemented

vc_pipe_packet — box anything, remember its type

A std::any under the hood. The unbox is a pointer-form any_cast — it returns nullptr on a type mismatch rather than throwing, so we raise our own vc_exception.

template <typename T>
  requires(!std::is_same_v<std::decay_t<T>, vc_pipe_packet>)   // keep copy/move on the special members
explicit vc_pipe_packet(T value) : value_(std::move(value)) {}   // sink: lvalue→copy, rvalue→move

template <typename T> const T& get() const {
    const T* held = std::any_cast<T>(&value_);   // &value_ → pointer form, no throw
    if (held == nullptr)
        throw vc::vc_exception(invalid_argument, "...type mismatch...");
    return *held;
}
Why by-value + move: pass an lvalue image and the parameter value is a copy; move only moves that copy into the any. Your original is untouched. Only an explicit std::move(img) at the call site moves the real thing.
The requires guard is belt-and-suspenders here. For a by-value constructor the special copy/move members already win over the template (non-template beats template on an exact-match tie). The guard would be load-bearing only if we switched to a forwarding-reference T&& — which is what std::any itself uses.

Mechanism 2 · the contract implemented

vc_pipe_contract — records slot types, looked up by name

A stage declares its slots by forwarding the typed descriptors from its own struct slots. Each add_*_slot lowers one to a private slot_decl. Direction is implicit — which vector holds it.

// inside a stage's declare():
contract.add_input_slot(slots::rgb);      // slot<vc_image>{"rgb"} — name + type, nothing else needed
contract.add_output_slot(slots::grey);    // slot<vc_image>{"grey"}

// what one push records:
slot_decl { name: "rgb", type: type_index(vc_image) }

// how the pipeline reads it back — a value, so a check is just ==
std::type_index t = contract.input_slot_type("rgb");   // THROWS vc_exception if never declared
The mechanism: a stage names+types its slots in exactly one place (its struct slots), declare() forwards them, and the pipeline reads the declarations back to validate. Because the lookup throws on an undeclared slot (this project's only error channel), validate() never carries a not-found branch — just the real type comparison.

Mechanism 3 · the per-run context implemented

vc_pipe_context — two maps, name → packet

One map for inputs, one for outputs (separate namespaces). The typed get_input(slot<T>) is thin sugar: look up the packet, then unbox it. The API is split by audience — the author uses typed slots, the runner uses names.

// author-facing: T is deduced from the descriptor, never spelled at the call site
template <typename T> const T& get_input(slot<T> s) const {
    return get_input(slot_name{s.name}).get<T>();   // map lookup + any_cast
}
template <typename T> void set_output(slot<T> s, vc_pipe_packet p);

// runner-facing: keyed by plain name — the pipeline only has names in hand
void set_input(const slot_name& name, vc_pipe_packet p);
const vc_pipe_packet& get_output(const slot_name& name) const;

// private:
std::unordered_map<slot_name, vc_pipe_packet> inputs_;
std::unordered_map<slot_name, vc_pipe_packet> outputs_;
Audience, not symmetry. An author only ever reads inputs and writes outputs, so the typed sugar lives there; the runner only writes inputs and reads outputs by name. That is why get_input has a typed form and get_output does not — not an oversight.

Mechanism 4 · the pipeline validate/run = TODO(you)

What gets stored when you assemble

add() and connect() are done — they just append to two vectors. Each stage carries its own name (i_pipe::name()), so there is no separate name field on the belt.

stages_       = [ ptr→grayscale("grey"), ptr→mean_brightness("mean") ]   // unique_ptr<i_pipe>
connections_  = [ { from:{"grey","grey"}, to:{"mean","image"} } ]      // two stage_ports

validate() — the algorithm yours to write

Compares declarations against declarations. No packet exists yet.

1. for each stage: make a vc_pipe_contract, call stage.declare(c), keep it keyed by stage.name().
2. for each connection {from, to}:            // from, to are stage_port {stage, slot}
     out_ty = contracts[from.stage].output_slot_type(from.slot)   // type_index — THROWS if undeclared
     in_ty  = contracts[to.stage].input_slot_type(to.slot)
     if (out_ty != in_ty) → throw    // the only branch — a missing slot already threw above

run() — the algorithm yours to write

The map variant: inject open inputs, execute in order, harvest open outputs (see the model below).

1. gather contracts (declare() each stage) → you know every stage's declared slot names.
2. open inputs  = all declared input slots  minus every connection's `to`
     open outputs = all declared output slots minus every connection's `from`
3. require `inputs` keys == open inputs EXACTLY (a missing OR extra key → throw).
4. for each stage in insertion order:
     ctx = vc_pipe_context{}
     move the caller's packets for this stage's open inputs → ctx.set_input(slot, …)
     for each connection whose `to.stage` == this stage:
         ctx.set_input(conn.to.slot, ctxs[conn.from.stage].get_output(conn.from.slot))
     stage.process(ctx)          // reads inputs, sets outputs
     keep ctx (its outputs feed downstream)
5. harvest: for each open output port → result[{stage, slot}] = ctx.get_output(slot)

run(), really · inject → execute → harvest

One shape for every graph. run() does three things, and the map keys fall out of the graph's boundary slots. A boundary slot is one no connection touches.

  1. Inject — the caller's map places packets on the graph's open input slots (an input no connection feeds).
  2. Execute — run stages in insertion order; each stage's outputs route along the connections to downstream inputs.
  3. Harvest — collect the packets left on the graph's open output slots (an output no connection consumes) and return them as a map.
std::unordered_map<stage_port, vc_pipe_packet>
run(std::unordered_map<stage_port, vc_pipe_packet> inputs) const;   // stage_port = { stage, slot }
Open = the graph boundary = the harness's job. Load feeds the open inputs; save drains the open outputs. Everything internal is driven by connect(). The map is taken by value as a sink — the runner moves each packet into a context, so an rvalue (a temporary or std::move) avoids a deep image copy.

▸ linear — 1 open in, 1 open out

grayscale → mean. One input and one output dangle, so the map has a single key on each side:

in : { {"grey","rgb"} → pkt }
out: { {"mean","mean"} → pkt }

▸ merge/blend — many open ins

Three sources = three open inputs. The stage_port key disambiguates the repeated slot names:

in : { {"blend","base"}    → pkt,
       {"blend","overlay"} → pkt,
       {"blend","mask"}    → pkt }
Resolved design point: an earlier draft weighed an auto-detecting run(packet) for the linear case against a map form for DAGs. It converged on one uniform currency — the map keyed by stage_port — so a linear chain is simply the one-open-in / one-open-out special case, no second API to maintain.

Constructing & running — real code

A · linear chain, single source current API

Load happens outside the pipeline (load is harness, not a stage) and is fed in through run().

using namespace vc::pipe;

// 1. load the source — harness, outside the pipe
vc::io::stb_image_reader reader;
vc::vc_image img = reader.read("photo.jpg");

// 2. construct + add stages. Each stage carries its OWN name; add() returns it.
vc_pipeline pipe;
const auto grey = pipe.add(std::make_unique<vc_grayscale_stage>("grey"));
const auto mean = pipe.add(std::make_unique<vc_mean_brightness_stage>("mean"));

// 3. wire output port → input port. A stage_port is { stage, slot<T> }.
pipe.connect({grey, vc_grayscale_stage::slots::grey},
             {mean, vc_mean_brightness_stage::slots::image});

// 4. check the wiring BEFORE any pixels move (throws on a type mismatch)
pipe.validate();

// 5. inject on the open input (grey.rgb); we're done with img, so MOVE it in.
std::unordered_map<stage_port, vc_pipe_packet> inputs;
inputs.emplace(stage_port{grey, vc_grayscale_stage::slots::rgb},
               vc_pipe_packet{std::move(img)});

const auto outputs = pipe.run(std::move(inputs));

// 6. read the result off its open-output port (mean.mean : double)
const double brightness =
    outputs.at(stage_port{mean, vc_mean_brightness_stage::slots::mean})
        .get<double>();
Why grey / mean instead of string literals? add() hands back the stage's name, so wiring never restates a literal that could drift. A stage_port{grey, slots::grey} is identical to one built from the raw string — code-wired and config-wired graphs are interchangeable.

B · a stage that captures configuration

The strategy/functor pattern: config in the constructor (after the name), held as a private member; process() stays const and only reads it.

class vc_blur_stage : public i_pipe {
  public:
    vc_blur_stage(stage_name name, float radius)
        : i_pipe(std::move(name)), radius_(radius) {}   // name → base, config → member

    const char* kind() const override { return "blur"; }   // per-type identity

    void declare(vc_pipe_contract& c) const override {
        c.add_input_slot(slots::in);
        c.add_output_slot(slots::out);
    }
    void process(vc_pipe_context& ctx) const override {
        const auto& src = ctx.get_input(slots::in);   // const vc_image&, type deduced
        // ... blur src using radius_, build result ...
        // ctx.set_output(slots::out, vc_pipe_packet{result});
    }

    struct slots {
        static constexpr slot<vc::vc_image> in{"in"};
        static constexpr slot<vc::vc_image> out{"out"};
    };
  private:
    float radius_;   // captured once at construction; process() only reads it
};

// constructed WITH its param — name first, then config
pipe.add(std::make_unique<vc_blur_stage>("blur", 2.5f));

C · many open ports — the same map form current API

A blend with three open inputs and one open output. Nothing new: the same run(map)→map, just more keys. Keyed by stage_port because slot names (e.g. every source's "rgb") repeat across stages. (vc_blend_stage illustrative.)

// blend declares open inputs base/overlay/mask and one open output "blended".
std::unordered_map<stage_port, vc_pipe_packet> inputs;
inputs.emplace(stage_port{"blend", vc_blend_stage::slots::base},    vc_pipe_packet{base});
inputs.emplace(stage_port{"blend", vc_blend_stage::slots::overlay}, vc_pipe_packet{over});
inputs.emplace(stage_port{"blend", vc_blend_stage::slots::mask},    vc_pipe_packet{mask});

const auto outputs = pipe.run(std::move(inputs));
vc::vc_image blended =
    outputs.at(stage_port{"blend", vc_blend_stage::slots::blended}).get<vc::vc_image>();

Ownership & lifetime — who holds what

vc_pipeline     owns   unique_ptr<i_pipe>        // sole owner of every stage
vc_pipe_context holds  vc_pipe_packet by value    // moved in, moved across connections
vc_pipe_packet  holds  std::any (heap)            // payload must be copyable
vc_image        holds  shared_ptr<buffer>         // COPY IS SHALLOW — shares pixels
The one guardrail: ctx.get_input(slots::in) returns const vc_image&, so a stage can only reach the buffer through pixels() (const) — never mutable_pixels(). A transform produces a new image rather than mutating a shared input. In-place mutation with an ownership check (use_count()==1) is a [LATER] performance move.
